### 修复的缺陷

- `McpClient._write` 未 drain（asyncio stdin 缓冲导致对端收不到）→ 改 async write + drain；
- `request` 返回整个 JSON-RPC 信封而非 result → 解包 result、error 抛错；
- fixture 在 Windows 用 GBK 写 stdout 导致客户端 UTF-8 解码崩溃 → 强制 UTF-8；
- `PluginTree._rollback` 只调 close() 不执行 apply 返回的 disposer（服务器进程会泄漏）→ 补执行（含 await）。

### 验证

- 全量测试 **86 passed**（78 + 8 新增）；headless/compileall/配置树（116 行）通过。

## 11. 设计取舍总览（剩余 🔶 项：情况 + 理由）

| # | 项 | 情况（TS 版 → Python 版） | 为什么取舍 |
|---|---|---|---|
| 1 | scope-filtered dispatch（`Scoped<T>`/`scopeTarget`） | TS 按作用域过滤事件派发；Python 用 scoped Context 做**服务层**隔离（preset/子代理），事件总线全局共享、载荷携带 agent 由监听者自滤 | 单进程 Python 里「按作用域过滤的服务仓库」已覆盖主要隔离需求（工具/分节/服务）；全局总线 + 载荷过滤省掉一套派发管线，监听者语义更直白 |
| 2 | `dsh-web-app`/`dsh-headless` 独立 bundle | TS 是两条独立 bundle 行；Python 共用 base.yml，web/headless 是 CLI 运行时接线（profile + 标志） | 单 bundle 无重复配置；PyCharm 开箱即用路径更短 |
| 3 | Agent Presets 完整版（roster/isolate realm/composeFrom） | TS 有 roster 管理 + isolate realm；Python 为 preset yml 行挂 agent 作用域 + 局部 ToolRuntime 委托 + recompose + scope_parent 继承 | 覆盖「预设组合进作用域 + 运行期换绑 + 子代理继承」三个硬需求；roster 是 UI 管理面，headless/PyCharm 场景价值低 |
| 4 | 动态 workflow 完整版（worker-thread） | TS 有 worker-thread 执行 + 完整事件；Python 为 phase 顺序/step 并行 in-process 子代理 + 结构化输出强制 + workflow/* 事件子集 | in-process 子代理复用 agent loop 全栈（prompt/管线/审批）；与 run_code/cordis 同一信任立场，无需跨进程隔离 |
| 5 | Code Mode 执行后端（18 号手册） | TS 有 worker-thread 隔离 + TS/Python 双 SDK；Python 为 in-process Python（协作式中止、stdout 捕获加锁、SDK 仅 Python） | 与 run_code 同信任立场；双语言 SDK 需要 Node 运行时，Python 版只需一种语言 |
| 6 | 自指 cordis client 半（19 号手册） | TS 有浏览器 client 运行时（React slot + 审批 UI）；Python 无浏览器运行时——client 半仅存储/预检，run → `client-half-failed` | 诚实拒绝优于假运行时：dsh_python 无 React slot 体系，能力移入 code.host 的指引写入拒绝消息 |
| 7 | 投影 checkpoint 缓存（20 号手册） | TS 有 session-projection-cache（冷读零全量加载）；Python 为 live-only（活跃会话驱动，冷读回落全量折叠） | 缓存是纯可选加速层；Python 内存折叠 O(n) 且仅在读取时发生，规模场景再上缓存 |
| 8 | e2b / Windows ACL（远端/深度平台件） | TS 支持 e2b 远端沙箱与 Windows ACL 细化；Python 为 Job Object + Landlock 双平台本机隔离 | 本机隔离已覆盖主要威胁模型；e2b 属远端部署形态，ACL 属更细粒度文件授权，均为增量而非缺口 |
